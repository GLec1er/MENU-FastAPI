# Надёжные фоновые задания для экспорта меню

## Цель и границы

Развить существующий экспорт меню в XLSX в первый тип надёжного фонового задания `menu_report`. После ответа `202 Accepted` задание и данные для его выполнения должны оставаться в PostgreSQL даже при недоступном RabbitMQ или падении worker. Повторная доставка может повторить вычисление, но для одного задания допускается только один зафиксированный результат.

Первый релиз выполняет только `menu_report`: произвольный код или пользовательские типы заданий через API не принимаются. Приложение сохраняет нынешние маршруты `/api/v1/report`, а новый API `/api/v1/jobs` предоставляет единое представление состояния. XLSX умеренного размера хранится в PostgreSQL; отдельное файловое хранилище и нагрузочные гарантии для больших отчётов в этот релиз не входят.

## Текущее состояние проекта

- `POST /api/v1/report/` читает меню и сразу вызывает `write_report.apply_async(...)`. Между приёмом запроса и публикацией нет записи задания в БД.
- Статус читается из Celery RPC backend. Он не является долговременным источником состояния задания.
- Worker пишет `app/data/{task_id}.xlsx`; результат не связан транзакцией со статусом и зависит от общего файлового пути.
- Проект уже использует FastAPI, PostgreSQL, SQLAlchemy/Alembic, Celery, RabbitMQ и Docker Compose. Существующие API-тесты не проверяют отказоустойчивость фоновых заданий.

## API и состояния

| Маршрут | Поведение |
| --- | --- |
| `POST /api/v1/jobs` с `{"kind":"menu_report"}` | Возвращает `202`, `id`, `kind`, `status="queued"`, число попыток и `Location: /api/v1/jobs/{id}` после коммита записи задания и outbox. |
| `GET /api/v1/jobs/{id}` | Возвращает состояние, `attempts`, `max_attempts`, время создания/обновления, код и безопасное описание последней ошибки; неизвестный ID даёт `404`. |
| `GET /api/v1/jobs?status=...&limit=20&offset=0` | Страничный список метаданных, в том числе ошибочных заданий; `limit` не больше 100. Тело XLSX и снимок меню в список не включаются. |
| `GET /api/v1/jobs/{id}/result` | Возвращает XLSX с постоянным именем `menu-report-{id}.xlsx` только для `succeeded`; неизвестный ID даёт `404`, известный без результата — `409`. |

Существующие `POST /api/v1/report/`, `GET /api/v1/report/{task_id}` и `GET /api/v1/report/{task_id}/download` остаются доступными и обращаются к тем же `jobs` и `job_results`. Старый формат `StatusMessage` сохраняется на маршрутах `/report`; ID присутствует в сообщении, как сейчас. Новый API возвращает структурированный ID и подробный статус.

Состояния: `queued`, `running`, `retry_wait`, `succeeded`, `failed`. `succeeded` и `failed` терминальны; автоматический повтор не меняет их. Отдельный признак публикации outbox не смешивается со статусом задания. Приём запроса не зависит от доступности RabbitMQ: недоступность PostgreSQL приводит к ошибке запроса, а не к `202`.

## Данные и компоненты

- `jobs`: UUID, тип, снимок меню в `JSONB`, состояние, число начатых попыток, лимит попыток, время следующей попытки, токен и срок владения worker, код/безопасное описание ошибки и временные метки. Снимок читается из PostgreSQL при создании, чтобы последующие правки меню не меняли уже принятое задание. Redis-кэш не служит источником этого снимка.
- `outbox`: UUID события, `job_id`, тип (`job.execute` или `job.failed`), номер попытки, номер повторной публикации, время доступности, время подтверждённой публикации и служебные данные повтора. Записи создаются в той же транзакции, что и соответствующий переход `jobs`. Уникальность `(job_id, тип, номер попытки, номер повторной публикации)` не даёт создавать одно логическое событие повторно при гонке диспетчеров; восстановление неподхваченного задания создаёт следующую публикацию с новым номером.
- `job_results`: `job_id` как первичный ключ и внешний ключ, MIME-тип, содержимое XLSX в `BYTEA`, SHA-256 и время создания. Результат и переход в `succeeded` фиксируются одной транзакцией.
- Outbox-диспетчер — отдельный процесс Docker Compose. Он выбирает доступные строки через `FOR UPDATE SKIP LOCKED`, публикует сообщения и отмечает строку отправленной только после подтверждения брокера. Ошибка публикации оставляет строку для новой попытки. Если процесс упал после подтверждения, но до отметки, повторная публикация допустима.
- Celery worker получает только `job_id`, номер попытки и ID события. Он читает снимок из PostgreSQL и использует БД как источник состояния; Celery result backend не используется для API статуса.
- Цикл сверки в процессе диспетчера каждые 10 секунд находит задания с истёкшим владением и планирует повтор или перевод в `failed`. Если `queued`/`retry_wait` не был захвачен worker через 120 секунд после подтверждённой публикации, сверка создаёт новую запись outbox для той же следующей попытки. Повторные события безопасны; до срока следующей попытки `retry_wait` не переотправляется.

RabbitMQ использует объявленные долговечные очереди для исполнения и `jobs.failed`, persistent-сообщения и publisher confirms. Маршрут публикации проверяется: неподтверждённое или не маршрутизированное сообщение оставляет outbox незавершённым. Публикация имеет таймаут 5 секунд и повторяется с задержкой. Версии контейнеров фиксируются вместо `latest`. Сообщения сериализуются как JSON; приём pickle отключается. `jobs.failed` получает терминальные ошибки через outbox: один только механизм RabbitMQ DLX не покрывает штатно обработанные ошибки приложения.

## Исполнение, повторы и сбои

1. API читает меню и создаёт `jobs` и `outbox(job.execute)` в одной транзакции. Ответ `202` отправляется только после коммита.
2. Диспетчер отправляет событие из outbox в RabbitMQ с подтверждением. При ошибке он повторяет публикацию с задержкой, не меняя принятое задание.
3. Worker атомарно захватывает доступное задание, только если номер попытки в сообщении равен `attempts + 1` и наступило время запуска. Он увеличивает `attempts`, выставляет `running`, уникальный токен владения и срок владения. Старое сообщение, дубликат для уже выполняемого или терминального задания завершается без нового результата.
4. Worker строит XLSX в памяти. При успехе он в одной транзакции вставляет строку `job_results` и переводит задание в `succeeded`, только если токен владения ещё действителен. Уникальный `job_results.job_id` и проверка токена защищают от конкурирующих и запоздавших worker.
5. При обычной ошибке первых двух попыток worker фиксирует причину и `retry_wait`, очищает владение и создаёт новое `job.execute` в outbox с задержкой. Всего допускаются три начатые попытки; задержки после первых двух — 5 и 30 секунд. Тестовая конфигурация может сокращать интервалы, сохраняя те же переходы.
6. После третьей ошибки либо истечения владения третьей попытки worker или процесс сверки переводит задание в `failed` и в той же транзакции создаёт `outbox(job.failed)`. Диспетчер отправляет уведомление с постоянным ID события в `jobs.failed`. PostgreSQL остаётся источником списка ошибок; сообщение RabbitMQ может доставляться повторно.

Celery подтверждает сообщение после завершения обработки (`acks_late`) и возвращает его при гибели процесса выполнения (`task_reject_on_worker_lost`). Жёсткий лимит выполнения — 300 секунд, срок владения — 360 секунд; оба значения сокращаются в тестовой конфигурации. При падении до фиксации результата задание будет переотправлено; при падении после коммита, но до ack повторная доставка увидит `succeeded` и завершится без второй строки результата. Если дубликат пришёл во время действующего владения, восстановление после падения обеспечивает процесс сверки. Непрерывно падающие задания ограничиваются числом попыток в PostgreSQL.

Содержимое исключений и stack trace остаются в логах; API выдаёт ограниченный код и безопасное сообщение. Невалидный тип задания отклоняется при создании. Невалидный снимок, который невозможно обработать, переводится в `failed` без бесполезных повторов и также попадает в очередь ошибок.

## Проверка и демонстрация

Обязательные проверки используют реальные PostgreSQL, RabbitMQ, outbox-диспетчер и Celery worker в Docker Compose. Тестовый профиль worker предоставляет барьеры непосредственно перед коммитом результата и сразу после него: тест ждёт сигнал барьера, останавливает процесс и запускает worker без барьера. Эта возможность не включается в обычном запуске. Точки сбоя не зависят от случайного попадания в короткий временной интервал.

| Сценарий | Ожидаемое доказательство |
| --- | --- |
| RabbitMQ недоступен во время `POST /jobs` | API возвращает `202`; `jobs` и outbox существуют; после восстановления брокера задание доходит до `succeeded`. |
| Worker остановлен во время построения XLSX | После восстановления и истечения владения задание снова исполняется и завершается; результат в БД один. |
| Worker остановлен после коммита результата, до ack | Повторная доставка сохраняет `succeeded`; `COUNT(job_results WHERE job_id=...) = 1`, SHA-256 не меняется. |
| Публикация одного outbox-события выполнена дважды или работают два worker | Одно задание и одна строка результата; статус не откатывается из `succeeded`. |
| Исполнение постоянно завершается ошибкой | Не более трёх попыток, терминальный `failed`, доступный через API; событие с постоянным ID появляется в `jobs.failed`. |
| Ошибка или отмена транзакции создания | Нет ответа `202` и нет задания без outbox-события. |

Существующие CRUD-тесты остаются обязательной регрессией. Проверка миграции Alembic выполняется на PostgreSQL. README описывает API, запуск процессов и воспроизводимую демонстрацию падений. Проверка «один результат» относится к одному сохранённому XLSX на `job_id`, а не к однократному запуску Python-функции.

## Очерёдность реализации

1. Миграция и API с атомарным приёмом задания, статусом и выдачей результата.
2. Outbox-диспетчер и надёжная публикация при недоступном брокере.
3. Исполнитель XLSX, фиксация результата и защита от повторной доставки.
4. Ограниченные повторы, сверка зависших заданий и очередь `jobs.failed`.
5. Интеграционные испытания с принудительными сбоями, документация и регрессия.
